Logging với request_id
Đề bài Cart API, bàn giao và nghiệm thu

What: OpenAPI

    Là gì: file YAML hoặc JSON mô tả path, method, parameter, body, response và lỗi.
    Tài liệu: Swagger UI, Redoc hoặc Scalar sinh trang /docs từ file này.
    Kiểm tra: validator dùng cùng file để chặn request sai và đối chiếu response.
    Khác tài liệu viết tay: công cụ phát hiện được khi code lệch spec.




Ví dụ: một operation trong spec
/carts/{cartId}/items:
  post:
    operationId: addCartItem
    parameters:
      - $ref: '#/components/parameters/CartId'
    requestBody:
      required: true
      content:
        application/json:
          schema: { $ref: '#/components/schemas/AddItemRequest' }
    responses:
      '201': { $ref: '#/components/responses/Cart' }
      '400': { $ref: '#/components/responses/Error' }





Ví dụ: schema của request body
components:
  schemas:
    AddItemRequest:
      type: object
      additionalProperties: false
      required: [product_id, quantity]
      properties:
        product_id: { type: string, format: uuid }
        quantity: { type: integer, minimum: 1, maximum: 10 }

    Validator đọc schema này: quantity: 0, quantity: "2" hoặc field lạ đều bị trả 400.


Contract-first và code-first
Contract-first

    Thứ tự: viết openapi.yaml trước, code sau.
    Validation: middleware đọc spec, ví dụ express-openapi-validator.

Code-first

    Thứ tự: viết schema trong code, sinh spec từ code.
    Ví dụ: zod kết hợp @asteasolutions/zod-to-openapi.



What: validation ở boundary
Schema kiểm tra được

    Kiểu và định dạng: quantity là integer, cartId là uuid.
    Giới hạn: quantity từ 1 đến 10, không có field lạ.

Cần code nghiệp vụ

    Dữ liệu trong DB: product có tồn tại và đang bán.
    Trạng thái: đủ tồn kho, cart chưa checkout.


Required, optional và null
Key có mặt hay không

    Required: key phải có trong object.
    Optional: key được phép vắng mặt.

Giá trị của key

    Null: chỉ hợp lệ khi schema cho phép type: [string, 'null'].
    Client: xử lý key vắng mặt khác với key bằng null.


What: status nào cho lỗi nào
Status 	Khi nào 	Ví dụ trong bài
400 	Request sai schema 	quantity bằng 0
404 	Resource trên URL không có trong DB 	cartId không tồn tại
409 	Xung đột với trạng thái hiện tại 	Hết tồn kho
422 	Body đúng schema, tham chiếu sai 	Product ngừng bán

What: error contract
{
  "code": "VALIDATION_ERROR",
  "message": "Request body không hợp lệ",
  "details": [{ "field": "quantity", "issue": "must be <= 10" }],
  "request_id": "7f3c2a9e-1b4d-4c8a-9e21-5d6f0a3b8c10"
}

    code: chuỗi cố định để client rẽ nhánh; message chỉ để hiển thị.
    500: cùng dạng JSON, không chứa stack trace, câu SQL hay secret.

What và Why: logging

    Why: response lỗi chỉ cho client biết lỗi gì; log cho biết lỗi xảy ra ở đâu.
    request_id: sinh cho mỗi request, trả trong header X-Request-Id và error body.
    Gợi ý thư viện: pino-http, winston hoặc morgan; nhóm tự chọn.
    Không ghi: password, token, header Authorization.


Bài tập: Cart API

    Người dùng: xem danh sách sản phẩm, tạo giỏ hàng, thêm, đổi số lượng và xóa sản phẩm trong giỏ.
    Nhóm tự dựng: project RESTful API, DB (eg: PostgreSQL), migration, seed và script reset DB; thư viện do nhóm chọn.
    Chưa làm tuần này: đăng nhập, checkout, thanh toán; cart được xác định bằng cartId.



		
		
		
		
		

DB: bảng products
CREATE TABLE products (
  id          uuid PRIMARY KEY,
  sku         text UNIQUE NOT NULL,
  name        text NOT NULL,
  price_cents integer NOT NULL CHECK (price_cents > 0),
  stock       integer NOT NULL CHECK (stock >= 0),
  is_active   boolean NOT NULL DEFAULT true
);

    Seed: 5 product; 3 đang bán còn hàng, 1 có stock = 0, 1 có is_active = false.



		
		
		
		
		

DB: bảng carts và cart_items
CREATE TABLE carts (
  id     uuid PRIMARY KEY,
  status text NOT NULL DEFAULT 'open'
         CHECK (status IN ('open', 'checked_out'))
);
CREATE TABLE cart_items (
  cart_id    uuid REFERENCES carts(id) ON DELETE CASCADE,
  product_id uuid REFERENCES products(id),
  quantity   integer NOT NULL CHECK (quantity BETWEEN 1 AND 10),
  PRIMARY KEY (cart_id, product_id)
);

    Seed: 1 cart có status = 'checked_out' để thử lỗi ghi vào cart đã đóng.

Đề bài: endpoint product và cart
Endpoint 	Hành vi
GET /products?limit=&offset= 	Product đang bán; limit 1-50, mặc định 20
POST /carts 	Tạo cart rỗng; 201, header Location
GET /carts/{cartId} 	Cart, items và subtotal_cents

Đề bài: endpoint item trong cart
Endpoint 	Body 	Thành công
POST /carts/{cartId}/items 	{ product_id, quantity } 	201, trả cart
PATCH /carts/{cartId}/items/{productId} 	{ quantity } 	200, trả cart
DELETE /carts/{cartId}/items/{productId} 	Không có 	204

Đề bài: rule nghiệp vụ và mã lỗi
Rule 	Vi phạm thì trả
Product tồn tại và đang bán 	422 PRODUCT_UNAVAILABLE
Số lượng không vượt tồn kho 	409 INSUFFICIENT_STOCK
Product chưa có trong cart khi thêm 	409 ITEM_ALREADY_IN_CART
Chỉ ghi vào cart đang mở 	409 CART_CLOSED

    Lỗi schema và URL: 400 VALIDATION_ERROR; 404 CART_NOT_FOUND, ITEM_NOT_FOUND.


Yêu cầu bàn giao
Hạng mục 	Yêu cầu
Setup 	README ghi lệnh tạo DB, chạy migration, seed, reset và server
API 	6 endpoint đúng method, path, status của đề bài
Documentation 	OpenAPI 3.1 đủ mọi status; /docs chạy được; có example
Validation 	Chạy từ cùng nguồn schema với spec; request sai không chạm DB
Error và logging 	Mọi lỗi theo error contract, kể cả 500; gợi ý log kèm request_id
Evidence 	Script chạy lại được cho mọi dòng của ma trận nghiệm thu


Ma trận nghiệm thu: request sai
Kịch bản 	Kết quả cần thấy
quantity bằng 0, 11 hoặc "2" 	400 VALIDATION_ERROR, details chỉ quantity
Thiếu product_id; body có field lạ 	400 VALIDATION_ERROR; DB không đổi
cartId không phải uuid 	400 VALIDATION_ERROR
cartId hợp lệ nhưng không tồn tại 	404 CART_NOT_FOUND

Ma trận nghiệm thu: nghiệp vụ và server
Kịch bản 	Kết quả cần thấy
Thêm 2 product rồi GET cart 	subtotal_cents bằng tổng tính tay từ seed
Product ngừng bán; vượt stock 	422 PRODUCT_UNAVAILABLE; 409 INSUFFICIENT_STOCK
Ghi vào cart đã checkout 	409 CART_CLOSED
Tắt PostgreSQL rồi gọi API 	500 đúng error contract, không có stack trace
So response thật với spec 	Mọi response ở hai bảng khớp schema

Các lỗi thường gặp

    Hai nguồn schema: spec viết một kiểu, validation trong code viết kiểu khác.
    Lỗi thư viện lọt ra: validator trả format riêng, không theo error contract.
    Tin client: nhận price từ body thay vì đọc từ DB.
    Dựa vào lỗi DB: vi phạm CHECK constraint thành 500 thay cho 400.


Presentation

    Problem: Cart API cần gì để nhóm khác dùng được mà không đọc source.
    Solution: contract-first hay code-first, thư viện đã chọn và lý do.
    Demo: gửi một request sai từ /docs, chỉ response lỗi và dòng log có cùng request_id.
    Evidence và trade-off: kết quả ma trận; kịch bản chưa kiểm tra.
