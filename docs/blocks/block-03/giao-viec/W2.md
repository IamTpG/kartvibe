# W2: Order API (`POST /orders`, hai client, ánh xạ lỗi, deadline)

**Bạn làm gì, một câu:** thêm vào `services/order/` có sẵn khả năng đặt hàng `POST /orders`, gọi Inventory bằng **REST hoặc gRPC** (chọn khi khởi động), và trả cho browser **cùng một response ngoài** ở cả hai chế độ, kể cả khi Inventory chậm hoặc tắt.

**Đầu ra:** thư mục `services/order/` (cả thư mục, đã sửa). Bạn không làm Inventory.

## 1. Việc cần làm

1. **Nền.** Lấy `kem-theo/order/` làm nền. **Không đổi** `GET /orders`, `seed.ts`, các bảng `orders` và `order_items`, và hợp đồng hiện có (đã có người dùng). Chỉ thêm. **Giữ nguyên `cors({ origin: '*' })`** đang có: trang UI demo gọi Order từ trình duyệt.
2. **Bảng đơn mới.** Khi khởi động tự tạo (`CREATE TABLE IF NOT EXISTS`) bảng `purchase_orders(id serial primary key, sku text not null, quantity int not null, reservation_id text not null, status text not null, created_at timestamptz not null default now())` trong database `kartvibe_order`.
3. **`POST /orders`** theo `PLAN-trich.md` mục 3.2. Kiểm hình dạng đầu vào: body là JSON object hợp lệ, `sku` là chuỗi, `quantity` là số nguyên; sai thì **400** `VALIDATION_ERROR`, không gọi Inventory. Miền giá trị (ví dụ `quantity` 0 hay 5000) do Inventory kiểm: Order **không** tự chặn, mà ánh xạ kết quả Inventory trả về.
4. **Hai client với một giao diện chung.** Ví dụ `reserve(sku, quantity, ctx) → { reservationId, available? }`, ném lỗi có kiểu cho: hết hàng, ngoài miền, quá hạn, không kết nối, khác. Chọn cài đặt khi khởi động theo `INVENTORY_PROTOCOL` (`rest` hoặc `grpc`; mặc định `rest`; giá trị khác thì báo lỗi rõ và thoát):
   - **REST:** `POST ${INVENTORY_REST_URL}/inventory/reservations`.
   - **gRPC:** client sinh từ **proto v2** (xem `MOI-TRUONG.md`) tới `INVENTORY_GRPC_ADDR`.
   Cả hai gửi `x-request-id` (lấy từ request vào, hoặc sinh mới) và `x-client-version: v2` (header hoặc metadata).
5. **Deadline.** `INVENTORY_DEADLINE_MS` (mặc định 500) cho **cả hai** client: REST dùng `AbortSignal.timeout`, gRPC dùng deadline của lời gọi. Quá hạn thì ánh xạ ra 504.
6. **Ánh xạ lỗi** theo bảng ở `PLAN-trich.md` mục 3.3 (cột Inventory gRPC, Inventory REST, Order trả ra ngoài), **giống nhau ở hai chế độ**. Với gRPC, hết hàng là `FAILED_PRECONDITION` **và** metadata `x-error-code` bằng `OUT_OF_STOCK`: dựa vào metadata chứ không chỉ vào status. Mọi lỗi khác không rõ thì 500 `INTERNAL_ERROR`; không để lộ stack trace.
7. **Khi thành công** thêm một dòng vào `purchase_orders` (trạng thái `CONFIRMED`), trả **201** `{"orderId": id, "sku", "quantity", "status": "CONFIRMED"}`. Nếu ghi DB lỗi sau khi Inventory đã giữ hàng: 500 `INTERNAL_ERROR`, log `reservationId`, **không bù trừ** (D14).
8. **`available`.** Với gRPC, đọc `available` từ reply bằng kiểm tra presence (`!== undefined`), **không suy ra 0 khi vắng**: log `available` là số, hoặc chuỗi `"absent"`. Không đưa `available` vào response ngoài. (Với REST không có field này, bỏ qua.)
    **Cô lập (quan trọng):** toàn bộ mã phụ thuộc vào hình dạng của `ReserveReply` ở phía gRPC, tức việc đọc `available` **và** hằng `clientVersion` (`"v2"`), phải nằm trong **một file duy nhất** (ví dụ `src/inventory/grpc-client.ts`; tên bạn tự chọn, ghi vào `HANDOVER.md`). Lý do: team lead sẽ dựng bản Order cũ (`order-v1`) bằng cách sinh lại `src/generated` từ proto **v1** và bỏ phần đọc `available` trong đúng file đó; nếu mã rải nhiều nơi, bản cũ sẽ không biên dịch được.
9. **Log** theo `PLAN-trich.md` mục 3.5: **hai dòng mỗi request**, cùng `requestId`: một `direction: "inbound"` (`POST /orders`, như logger hiện có) và một `direction: "outbound"` cho lời gọi Inventory (`protocol`, `operation: "Reserve"`, `status`, `grpcStatus` nếu gRPC, `ms`, `clientVersion: "v2"`, `errorCode` nếu có, `available`, `reservationId`). Chỉ một dòng nghiệp vụ mỗi hướng, không log `/health` và `/_metrics`.
10. **Test hook** (chỉ khi `ENABLE_TEST_HOOKS=1`): `POST /_reset` xóa `purchase_orders` và đặt lại bộ đếm id (`TRUNCATE ... RESTART IDENTITY`), trả 204.
11. **Hợp đồng và kiểu:** cập nhật `src/contract.ts` rồi `npm run openapi` để `openapi.json` có `POST /orders` (các mã 201, 400, 409, 503, 504, 500) và `/_reset`. Hợp đồng cũ không đổi.
12. **Sinh code gRPC:** thêm script `npm run codegen` (lệnh ở `MOI-TRUONG.md`) sinh vào `src/generated/`, **commit** mã sinh ra. Phiên bản gRPC trong `package.json` ghim chính xác (không dấu `^`) theo `MOI-TRUONG.md`: bản Order cũ sẽ được dựng từ bản sao của thư mục này.
13. **Chạy hai chế độ cùng lúc:** cùng mã nguồn, chạy hai tiến trình: `PORT=4002 INVENTORY_PROTOCOL=rest` và `PORT=4012 INVENTORY_PROTOCOL=grpc`. Ghi hai lệnh đó vào README.
14. **`npm run check`:** tự kiểm tra, **dùng Inventory giả do bạn tự viết** trong `test/` (REST và gRPC, theo hợp đồng 3.3; bàn giao cùng để chạy được `npm run check`, không phải sản phẩm nộp), chạy hai chế độ, in PASS/FAIL và thoát 0 nếu đạt. Tối thiểu các ca, **mỗi ca ở cả hai chế độ và phải ra cùng response ngoài**:
    - đủ hàng → 201; hết hàng → 409 `OUT_OF_STOCK`; `quantity` 0 → 400; body không phải JSON → 400; `quantity` là chuỗi → 400;
    - Inventory giả chậm hơn deadline → 504 `INVENTORY_TIMEOUT` **trong khoảng thời gian hữu hạn** (kiểm thời gian thật, ví dụ < deadline + 500 ms);
    - Inventory tắt → 503 `INVENTORY_UNAVAILABLE`, cũng trong thời gian hữu hạn;
    - Inventory trả lỗi lạ → 500;
    - log có đúng hai dòng cho một request và `protocol` đúng chế độ.

## 2. Bạn được tự quyết

Cách đặt lớp client, tên lỗi nội bộ, cách đo deadline, cấu trúc thư mục `src/`, cách viết Inventory giả, thư viện phụ trợ nhỏ (ghi vào `HANDOVER.md`).

## 3. Bạn không được đổi

D1 đến D15 và mục 3: mã HTTP và `code` của response ngoài, bảng ánh xạ lỗi, tên biến môi trường và mặc định, cổng, tên bảng `purchase_orders`, tên khóa `x-error-code`, phiên bản thư viện, nội dung `.proto`.

## 4. Kèm theo

- `kem-theo/order/`: bản sao `services/order/` hiện có (không `node_modules`), là **nền** của bạn.
- `kem-theo/proto/inventory/v1` và `v2`: hợp đồng gRPC đóng băng. Client của bạn sinh từ **v2**.

## 5. Tiêu chí xong

- `npm run check` thoát 0 ở cả hai chế độ.
- Cùng một cặp request cho **cùng status và body** (sau khi bỏ `orderId`) ở cổng 4002 và 4012.
- `GET /orders?userId=1` vẫn đúng như trước (bạn không phá phần có sẵn).
- `HANDOVER.md` đã điền, đặt ở `W2-giao/`, ghi rõ **danh sách file đã đổi** so với `kem-theo/order/`.
